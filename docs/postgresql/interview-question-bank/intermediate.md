| IQ001 | Why is SQL called declarative? | You specify the desired result/state change while the optimizer chooses an execution strategy. | Separates relational semantics from physical access path. | “SQL executes clauses exactly top-to-bottom as written.” | Logical vs physical order? | 03 — SQL Overview |
| IQ002 | What is logical SELECT processing order? | Conceptually FROM/JOIN, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT/FETCH. | Explains alias visibility and aggregate semantics without claiming physical order. | “It is the exact executor plan.” | Where can planner reorder work? | 24 — SELECT Fundamentals |

| IQ010 | How do you debug unexpected duplicate join rows? | Establish intended output grain, inspect uniqueness/cardinality and predicates, count after each join; do not mask with DISTINCT. | Duplicates usually reflect real multiplicity or missing conditions. | “Add DISTINCT.” | How model many-to-many? | 30 — Joins |

| IQ012 | What does LATERAL do? | Lets a FROM item reference columns from preceding FROM items. | Powerful for top-N per parent and set-returning functions. | “It is just another LEFT JOIN keyword.” | Give top-1-order example. | 32 — Lateral Queries |

| IQ014 | ROW_NUMBER vs RANK vs DENSE_RANK? | ROW_NUMBER uniquely sequences rows; RANK shares ties with gaps; DENSE_RANK shares ties without gaps. | Choose according to tie semantics. | “They differ only in performance.” | Which solves third distinct salary? | 37 — Window Functions |
| IQ015 | What is a window frame? | The subset of a window partition relative to the current row used by frame-sensitive functions/aggregates. | ORDER BY alone does not fully define running/window semantics. | “Same as PARTITION BY.” | ROWS vs RANGE? | 37 — Window Functions |
| IQ016 | Why is LAST_VALUE often surprising? | Default frame typically ends at current peer group/current row, so LAST_VALUE may not mean final partition value. | Must define an appropriate frame for full-partition last value. | “LAST_VALUE always returns partition’s last row.” | Write the full frame. | 37 — Window Functions |

| IQ018 | Are PostgreSQL CTEs always materialized? | No; eligible non-recursive CTEs can be inlined. MATERIALIZED/NOT MATERIALIZED influence behavior. | Modern PostgreSQL differs from old versions/tutorial folklore. | “WITH always stores a temp result.” | When force materialization? | 34 — CTEs |

| IQ020 | UNION vs INTERSECT vs EXCEPT? | Union combines sets, intersect keeps common rows, except keeps left rows absent from right; default forms dedupe. | They are horizontal set operations over compatible columns. | “They join tables by keys.” | Why prefer UNION ALL sometimes? | 33 — Set Operations |
| IQ021 | What is `IS DISTINCT FROM`? | Null-safe inequality treating NULL as a comparable state; inverse is IS NOT DISTINCT FROM. | Avoids verbose null comparison logic. | “Same as `<>`.” | Use it in change detection. | 19 — NULL |
| IQ022 | Why can a CHECK allow NULL? | A CHECK rejects FALSE, while UNKNOWN from a NULL-dependent expression is not FALSE. | Pair with NOT NULL when absence is invalid. | “CHECK(value > 0) implies NOT NULL.” | Show correct positive required column. | 42 — Constraints |

| IQ025 | `text` vs `varchar(n)` in PostgreSQL? | `text` is appropriate for unconstrained strings; `varchar(n)` expresses a genuine maximum, not a performance optimization. | PostgreSQL does not reward arbitrary length limits as many assume. | “varchar is always faster/smaller.” | When use `char(n)`? | 11 — Strings |
