# Q211–Q280 — Senior JavaScript Engineering

## Memory, GC and weak references

**Q211. What does garbage collection guarantee in JavaScript?** — **Expected:** Unreachable objects may be reclaimed according to implementation policy; collection timing and memory layout are not application-controlled language guarantees. **Reasoning:** Correctness cannot depend on GC timing. **Common incorrect:** “Objects are freed immediately when a variable leaves scope.” **Follow-up:** What is reachability? **Related:** [Memory mental model](../37-47-advanced-language-apis.md#42--memory-mental-model).

**Q212. Why is “primitives live on stack, objects on heap” a poor JavaScript guarantee?** — **Expected:** Engines are free to optimize representation; stack/heap is a useful implementation model, not normative ECMAScript semantics. **Reasoning:** Observable semantics matter, not storage folklore. **Common incorrect:** “Spec mandates primitives on stack.” **Follow-up:** What memory model is safer for interviews? **Related:** [Memory mental model](../37-47-advanced-language-apis.md#42--memory-mental-model).

**Q213. What creates a memory leak in a garbage-collected language?** — **Expected:** No-longer-useful data remains reachable from roots through references. **Reasoning:** GC cannot infer business usefulness. **Common incorrect:** “Any allocation that isn't manually freed.” **Follow-up:** Give a DOM listener example. **Related:** [Memory leaks](../internals-performance-debugging.md#73--memory-leaks).

**Q214. How can an event listener leak memory?** — **Expected:** A long-lived target retains the callback, which can retain closures and object/DOM graphs until listener is removed or target becomes unreachable. **Reasoning:** Follow retaining path. **Common incorrect:** “Listeners are weak by default.” **Follow-up:** How can AbortSignal help? **Related:** [Memory leaks](../internals-performance-debugging.md#73--memory-leaks).

**Q215. How can timers contribute to leaks?** — **Expected:** Active timers retain callbacks/captured state; intervals can remain reachable indefinitely if not cleared/lifecycle-bound. **Reasoning:** Host scheduler owns callback reference. **Common incorrect:** “Timer ID itself causes the leak.” **Follow-up:** Cleanup pattern? **Related:** [Memory leaks](../internals-performance-debugging.md#73--memory-leaks).

**Q216. When is WeakMap appropriate?** — **Expected:** Metadata/cache keyed by object lifetime where entries should disappear when keys are no longer strongly reachable. **Reasoning:** Weak key does not keep object alive. **Common incorrect:** “A Map that uses less memory and is always preferable.” **Follow-up:** Why can't you enumerate it? **Related:** [Collections](../builtins-iteration-binary.md#26--map-set-weakmap-weakset).

**Q217. What is WeakRef for?** — **Expected:** Specialized access to an object without keeping it strongly alive, usually cache-like scenarios. **Reasoning:** `deref()` may return undefined depending on GC. **Common incorrect:** “Reliable way to know when object was deleted.” **Follow-up:** Why not use for locks? **Related:** [WeakRef](../37-47-advanced-language-apis.md#41--weakref-and-finalizationregistry).

**Q218. Why is FinalizationRegistry unsuitable for correctness-critical cleanup?** — **Expected:** Finalizer execution is nondeterministic and may be delayed or never occur before process/page ends. **Reasoning:** GC is not resource-lifetime protocol. **Common incorrect:** “Finalizers run immediately after last reference.” **Follow-up:** What standardized mechanism is deterministic? **Related:** [WeakRef](../37-47-advanced-language-apis.md#41--weakref-and-finalizationregistry).

**Q219. How do you prove a suspected browser memory leak?** — **Expected:** Reproduce repeated lifecycle, compare heap snapshots/retainers after GC opportunities, find unexpected roots/retaining paths, fix lifecycle edge, verify objects stop accumulating. **Reasoning:** Rising RSS alone isn't proof. **Common incorrect:** “Task Manager memory rose once.” **Follow-up:** Detached DOM example? **Related:** [Memory leaks](../internals-performance-debugging.md#73--memory-leaks).

**Q220. What can unresolved async workflows retain?** — **Expected:** Promise reactions, closures, queued work, abort listeners, request state, and referenced data can remain reachable while workflow is pending/registered. **Reasoning:** Async lifecycle has memory ownership. **Common incorrect:** “Promises are automatically weak.” **Follow-up:** How does cancellation help? **Related:** [Memory leaks](../internals-performance-debugging.md#73--memory-leaks).

## Engine and performance reasoning

**Q221. Name major JavaScript engines.** — **Expected:** V8, SpiderMonkey, JavaScriptCore are major examples. **Reasoning:** Engine is implementation, not language spec. **Common incorrect:** “Node.js is an engine.” **Follow-up:** Which engine does Node commonly embed? **Related:** [Engines](../internals-performance-debugging.md#70--javascript-engines).

**Q222. What is JIT compilation conceptually?** — **Expected:** Runtime uses observed execution/profiling to compile/optimize code into machine-code tiers while preserving ECMAScript semantics. **Reasoning:** Implementation strategy can change. **Common incorrect:** “All JS is interpreted only.” **Follow-up:** What is deoptimization? **Related:** [JIT](../internals-performance-debugging.md#71--jit-and-optimization-mental-models).

**Q223. What is an inline cache?** — **Expected:** Engine optimization structure that records observed property/call patterns to speed repeated operations under assumptions. **Reasoning:** Implementation-specific optimization, not JS API. **Common incorrect:** “Browser HTTP cache.” **Follow-up:** How can unstable object shapes affect it? **Related:** [JIT](../internals-performance-debugging.md#71--jit-and-optimization-mental-models).

**Q224. What does monomorphic vs polymorphic call/property site mean?** — **Expected:** A site repeatedly observes one shape/target versus several; engines may optimize simpler stable patterns differently. **Reasoning:** Optimization mental model only. **Common incorrect:** “A language type-system feature.” **Follow-up:** Should you rewrite code solely to be monomorphic? **Related:** [JIT](../internals-performance-debugging.md#71--jit-and-optimization-mental-models).

**Q225. What is deoptimization?** — **Expected:** Engine abandons/backs off optimized code when assumptions/guards no longer hold and continues with a less-specialized tier. **Reasoning:** Correctness remains intact. **Common incorrect:** “A thrown JavaScript exception.” **Follow-up:** Why is this not normally visible semantically? **Related:** [JIT](../internals-performance-debugging.md#71--jit-and-optimization-mental-models).

**Q226. First rule of JavaScript performance work?** — **Expected:** Measure a real user/system bottleneck before optimizing. **Reasoning:** CPU, network, rendering, memory, startup need different fixes. **Common incorrect:** “Always replace map with for loop.” **Follow-up:** Which DevTools panel for long tasks? **Related:** [Performance](../internals-performance-debugging.md#72--javascript-performance).

**Q227. Why is algorithmic complexity often more important than syntax micro-benchmarks?** — **Expected:** O(n²) or repeated scans can dominate at scale regardless of tiny operator/method differences. **Reasoning:** Growth rate beats local micro-cost. **Common incorrect:** “Modern engines optimize all algorithms equally.” **Follow-up:** Example replacing array lookup with Map? **Related:** [Performance](../internals-performance-debugging.md#72--javascript-performance).

**Q228. What is a main-thread long task problem?** — **Expected:** Long synchronous work blocks input handling/rendering and increases responsiveness latency. **Reasoning:** Browser UI shares main-thread scheduling with JS tasks. **Common incorrect:** “Promise callbacks are always off-thread.” **Follow-up:** Worker vs chunking choice? **Related:** [Performance](../internals-performance-debugging.md#72--javascript-performance).

**Q229. Why can excessive allocation hurt performance even if GC is fast?** — **Expected:** High allocation rate increases GC pressure/work and can create retained-memory pressure. **Reasoning:** Allocation has lifecycle costs. **Common incorrect:** “GC makes allocation free.” **Follow-up:** What should you measure? **Related:** [Performance](../internals-performance-debugging.md#72--javascript-performance).

**Q230. What is layout thrashing?** — **Expected:** Interleaving DOM writes that invalidate layout with reads requiring fresh geometry can force repeated synchronous layout work. **Reasoning:** Host rendering pipeline cost. **Common incorrect:** “Any DOM loop.” **Follow-up:** Mitigation? **Related:** [Performance](../internals-performance-debugging.md#72--javascript-performance).

**Q231. Why can `Promise.all(hugeList.map(fetch))` be harmful?** — **Expected:** Launches unbounded concurrency, increasing sockets, server load, memory and retry storms. **Reasoning:** Async concurrency is a resource policy. **Common incorrect:** “Promise.all serializes safely.” **Follow-up:** How implement bound? **Related:** [Concurrency](../architecture-and-production.md#85--concurrency-and-race-conditions).

**Q232. What is a performance budget?** — **Expected:** Measurable limits for user/system metrics such as bundle size, long tasks, interaction latency, memory, or API latency. **Reasoning:** Turns performance into governance. **Common incorrect:** “A one-time Lighthouse score.” **Follow-up:** Staff-level enforcement? **Related:** [Performance](../internals-performance-debugging.md#72--javascript-performance).

**Q233. Memoization trade-off?** — **Expected:** Saves repeated computation at cost of memory, key management, invalidation and complexity; valuable only with reuse/hit rate. **Reasoning:** Cache has ownership/lifetime. **Common incorrect:** “Memoize every pure function.” **Follow-up:** WeakMap cache use? **Related:** [Performance](../internals-performance-debugging.md#72--javascript-performance).

**Q234. Why can code splitting improve startup but hurt performance?** — **Expected:** Less initial parse/download can help, but too many chunks add network waterfalls/coordination/cache overhead. **Reasoning:** Optimize whole delivery path. **Common incorrect:** “More chunks always faster.” **Follow-up:** What should guide route split? **Related:** [Performance](../internals-performance-debugging.md#72--javascript-performance).

**Q235. What should a senior engineer say about hidden classes/shapes?** — **Expected:** Useful engine-specific model for stable property layouts, but not ECMAScript guarantee; profile target engines before shape-driven rewrites. **Reasoning:** Separate implementation from semantics. **Common incorrect:** “All engines implement identical hidden classes.” **Follow-up:** Why prototype mutation may disrupt optimization? **Related:** [JIT](../internals-performance-debugging.md#71--jit-and-optimization-mental-models).

## Debugging and production investigation

**Q236. How do you investigate a non-obvious production JS bug?** — **Expected:** Reproduce/collect evidence, define invariant, narrow inputs/timing, inspect stack/network/state, form and falsify hypotheses, identify root cause, add regression/observability. **Reasoning:** Scientific debugging. **Common incorrect:** “Add logs until it disappears.” **Follow-up:** How minimize a race reproduction? **Related:** [Debugging](../internals-performance-debugging.md#74--debugging).

**Q237. What are conditional breakpoints useful for?** — **Expected:** Pause only when state/input matches failure condition in noisy loops/events. **Reasoning:** Reduce debugging perturbation/noise. **Common incorrect:** “They change code behavior intentionally.” **Follow-up:** Logpoints alternative? **Related:** [Debugging](../internals-performance-debugging.md#74--debugging).

**Q238. Why inspect the call stack and scopes together?** — **Expected:** Stack shows execution path; scope view shows actual bindings/closures/shadowing at each frame. **Reasoning:** Many JS bugs are value+control-flow interactions. **Common incorrect:** “Stack contains variable values automatically.” **Follow-up:** TDZ/shadowing example? **Related:** [Debugging](../internals-performance-debugging.md#74--debugging).

**Q239. What are source maps for?** — **Expected:** Map generated/transformed bundle locations back to original sources for debugging. **Reasoning:** Tooling metadata, not ECMAScript. **Common incorrect:** “They ship source code execution to browser.” **Follow-up:** Security/deployment consideration? **Related:** [Debugging](../internals-performance-debugging.md#74--debugging).

**Q240. How would you debug a stale-response UI bug?** — **Expected:** Record request generation/query/start/finish, reproduce out-of-order completion, prove older result commits after newer, then abort/tag and guard state transition. **Reasoning:** Race over async turns. **Common incorrect:** “Add debounce only.” **Follow-up:** Why debounce doesn't guarantee order? **Related:** [Concurrency](../architecture-and-production.md#85--concurrency-and-race-conditions).

**Q241. How would you debug a circular module failure?** — **Expected:** Inspect import graph and which export is read during initialization; identify uninitialized live binding and break/restructure cycle or defer access. **Reasoning:** Module instantiation/evaluation. **Common incorrect:** “Add setTimeout around import.” **Follow-up:** Lower-level shared module pattern? **Related:** [Modules](../36-modules.md).

**Q242. What does “pause on caught exceptions” help find?** — **Expected:** Errors swallowed/translated by code/framework can be inspected at original throw site. **Reasoning:** Catch layer may obscure cause. **Common incorrect:** “Only uncaught errors can be debugged.” **Follow-up:** How avoid drowning in expected exceptions? **Related:** [Debugging](../internals-performance-debugging.md#74--debugging).

**Q243. What is a reproducible bug report for async issue?** — **Expected:** Inputs, environment/version, exact action/timing, expected/actual, logs/network trace/correlation IDs, minimum reproduction if possible. **Reasoning:** Timing bugs need evidence. **Common incorrect:** “Sometimes broken.” **Follow-up:** How inject deterministic delays in tests? **Related:** [Testing](../architecture-and-production.md#84--testing-javascript).

**Q244. Why can console logging change timing bugs?** — **Expected:** Logging adds work/serialization/devtools interaction and can perturb scheduling/performance. **Reasoning:** Instrumentation has observer effect. **Common incorrect:** “console has zero cost.” **Follow-up:** Better trace metadata? **Related:** [Debugging](../internals-performance-debugging.md#74--debugging).

**Q245. How do you verify a performance fix?** — **Expected:** Same workload/environment, before/after measurements, user-relevant metric, variance/sample size, regression guard/budget. **Reasoning:** Avoid anecdotal improvement. **Common incorrect:** “Code looks faster.” **Follow-up:** What if microbenchmark improves but UX worsens? **Related:** [Performance](../internals-performance-debugging.md#72--javascript-performance).

## Security and trust boundaries

**Q246. What is prototype pollution in a merge helper?** — **Expected:** Untrusted keys/path can mutate prototypes or create inherited properties affecting later logic. **Reasoning:** Object inheritance becomes data-to-behavior channel. **Common incorrect:** “Only modifying Object.prototype directly in source.” **Follow-up:** Mitigations? **Related:** [Prototypes](../16-prototypes.md).

**Q247. Why is `obj[key] = value` risky with untrusted key paths?** — **Expected:** Certain recursive/path semantics can reach prototype/constructor properties or overwrite sensitive fields; keys need schema/allowlist handling. **Reasoning:** Dynamic property access crosses trust boundary. **Common incorrect:** “Bracket notation sanitizes keys.” **Follow-up:** Map/null-prototype use? **Related:** [Security](../paradigms-patterns-browser.md#62--browser-security-for-javascript-developers).

**Q248. What is Trusted Types conceptually?** — **Expected:** Browser security mechanism restricting dangerous DOM sinks to values produced by approved policies, reducing DOM XSS paths. **Reasoning:** Defense in depth around sinks. **Common incorrect:** “Automatic HTML sanitizer.” **Follow-up:** Still need correct policy/sanitization? **Related:** [Security](../paradigms-patterns-browser.md#62--browser-security-for-javascript-developers).

**Q249. Why is CSP not sufficient to make unsafe `innerHTML` acceptable?** — **Expected:** CSP reduces execution paths but unsafe DOM injection can still create vulnerabilities/markup manipulation and policies can be incomplete; code should keep untrusted data out of dangerous sinks. **Reasoning:** Defense in depth. **Common incorrect:** “CSP means XSS impossible.” **Follow-up:** Safe text default? **Related:** [Security](../paradigms-patterns-browser.md#62--browser-security-for-javascript-developers).

**Q250. What is an open redirect?** — **Expected:** Application navigates to attacker-controlled destination based on insufficiently validated redirect input. **Reasoning:** Trusted origin can become phishing/flow pivot. **Common incorrect:** “A CORS error.” **Follow-up:** Safe redirect policy? **Related:** [URL APIs](../paradigms-patterns-browser.md#57--url-apis).

**Q251. Why should logs redact tokens/credentials?** — **Expected:** Logs are widely replicated/accessed and can turn transient secrets into durable compromise. **Reasoning:** Observability is a trust boundary. **Common incorrect:** “Server logs are private enough.” **Follow-up:** What identifiers can be logged instead? **Related:** [Error architecture](../architecture-and-production.md#86--error-architecture).

**Q252. Why are third-party scripts high privilege?** — **Expected:** Same-origin page scripts can access DOM/data/APIs available to page unless isolated; a compromised third party becomes application compromise. **Reasoning:** Script supply chain is authority. **Common incorrect:** “External CDN scripts run in sandbox automatically.” **Follow-up:** Mitigations? **Related:** [Security](../paradigms-patterns-browser.md#62--browser-security-for-javascript-developers).

**Q253. What is SRI useful for?** — **Expected:** Subresource Integrity lets browser verify fetched static resource content matches expected hash where applicable. **Reasoning:** Detect unexpected CDN/resource modification. **Common incorrect:** “SRI updates dependencies automatically.” **Follow-up:** Limitation for dynamic third-party scripts? **Related:** [Security](../paradigms-patterns-browser.md#62--browser-security-for-javascript-developers).

**Q254. Why is client-side authorization insufficient?** — **Expected:** User controls browser/client; hiding/disabling UI does not prevent crafted requests. Trusted server must enforce authorization. **Reasoning:** Client is not security boundary. **Common incorrect:** “Button hidden means endpoint safe.” **Follow-up:** What should client checks do? **Related:** [Security](../paradigms-patterns-browser.md#62--browser-security-for-javascript-developers).

**Q255. What is a safe strategy for untrusted URLs?** — **Expected:** Parse with URL, constrain allowed schemes/origins/paths according to use, encode components, avoid passing arbitrary URLs to navigation/HTML sinks. **Reasoning:** Context-specific validation. **Common incorrect:** “Regex for `https` prefix only.” **Follow-up:** Why `javascript:` matters? **Related:** [URL APIs](../paradigms-patterns-browser.md#57--url-apis).

## Testing and validation

**Q256. Unit vs integration test?** — **Expected:** Unit isolates small logic/contract; integration verifies multiple real modules/adapters collaborate. **Reasoning:** Different confidence/failure localization. **Common incorrect:** “Integration is just slower unit test.” **Follow-up:** Where test fetch parser? **Related:** [Testing](../architecture-and-production.md#84--testing-javascript).

**Q257. Why can excessive mocks harm tests?** — **Expected:** They couple tests to implementation and can validate fake interactions instead of real contracts. **Reasoning:** Refactors break tests without behavior change. **Common incorrect:** “More mocks always isolate better.” **Follow-up:** What boundaries deserve doubles? **Related:** [Testing](../architecture-and-production.md#84--testing-javascript).

**Q258. What makes async tests deterministic?** — **Expected:** Explicit control of clocks/promises/network doubles, awaiting all owned work, isolated state, and avoiding real timing where unnecessary. **Reasoning:** Remove scheduler/network randomness. **Common incorrect:** “Sleep 1 second.” **Follow-up:** How simulate out-of-order responses? **Related:** [Testing](../architecture-and-production.md#84--testing-javascript).

**Q259. Fake timer limitation?** — **Expected:** Fake timers simulate selected scheduling APIs and may not reproduce browser rendering/event-loop/network behavior exactly. **Reasoning:** Useful unit control, not full host. **Common incorrect:** “Fake timer makes integration identical to browser.” **Follow-up:** What deserves real browser test? **Related:** [Testing](../architecture-and-production.md#84--testing-javascript).

**Q260. What is test isolation?** — **Expected:** Each test leaves no leaked global/module state, timers, listeners, storage, mocks, network handlers, random clock changes, or shared mutations. **Reasoning:** Order independence. **Common incorrect:** “Each test file has own name.” **Follow-up:** Cleanup patterns? **Related:** [Testing](../architecture-and-production.md#84--testing-javascript).

**Q261. Why runtime validation in JavaScript/TypeScript app?** — **Expected:** External data is unknown at runtime; TypeScript erases static types and JavaScript doesn't enforce them. **Reasoning:** Trust boundary parsing. **Common incorrect:** “Type annotation protects API response.” **Follow-up:** Parse-don't-validate? **Related:** [Runtime validation](../architecture-and-production.md#80--runtime-validation).

**Q262. `typeof` limitation for validation?** — **Expected:** Broad categories, `null` reports object, arrays/objects share object category, custom shapes not enforced. **Reasoning:** Need purpose-specific structural/schema checks. **Common incorrect:** “typeof gives exact class.” **Follow-up:** Array check? **Related:** [Runtime validation](../architecture-and-production.md#80--runtime-validation).

**Q263. `instanceof` limitation for validation?** — **Expected:** Prototype identity can differ across realms/custom `Symbol.hasInstance`; plain JSON objects aren't class instances. **Reasoning:** Use when prototype/brand is real contract. **Common incorrect:** “Best universal type checker.” **Follow-up:** Array cross-realm check? **Related:** [Runtime validation](../architecture-and-production.md#80--runtime-validation).

**Q264. What does “parse, don't validate” mean?** — **Expected:** Convert unknown boundary input into trusted domain representation once, rejecting invalid data, rather than keep untrusted shape and repeatedly test it. **Reasoning:** Trust state becomes explicit. **Common incorrect:** “Never validate.” **Follow-up:** API JSON example? **Related:** [Runtime validation](../architecture-and-production.md#80--runtime-validation).

**Q265. What should network mocks include beyond happy JSON?** — **Expected:** status failures, network errors, malformed payloads, latency/race, cancellation, retries, partial responses as contract requires. **Reasoning:** Production failures are part of API. **Common incorrect:** “Only 200 fixture.” **Follow-up:** Which failure does fetch reject? **Related:** [Testing](../architecture-and-production.md#84--testing-javascript).

## API design and error architecture

**Q266. Why prefer options object for growing API?** — **Expected:** Names optional parameters, allows additive extension, reduces positional ambiguity. **Reasoning:** Better backward evolution. **Common incorrect:** “Options objects are always faster.” **Follow-up:** When positional is fine? **Related:** [API design](../architecture-and-production.md#79--api-design-in-javascript).

**Q267. What belongs in an async function contract?** — **Expected:** Inputs/result, rejection/error taxonomy, cancellation, timing/ordering, mutation/side effects, retry/idempotency expectations. **Reasoning:** Promise return alone is incomplete. **Common incorrect:** “Just returns Promise<T>.” **Follow-up:** Event reentrancy equivalent? **Related:** [API design](../architecture-and-production.md#79--api-design-in-javascript).

**Q268. How should a library expose errors?** — **Expected:** Stable error classes/codes/data/cause with documented handling, not message parsing or raw transport errors. **Reasoning:** Messages can change/localize. **Common incorrect:** “Consumers should regex error.message.” **Follow-up:** Backward compatibility of error codes? **Related:** [Error architecture](../architecture-and-production.md#86--error-architecture).

**Q269. Expected vs unexpected errors?** — **Expected:** Expected operational/domain outcomes callers can handle should be modeled/documented; invariant/programmer defects should surface loudly and be fixed. **Reasoning:** Recovery policy differs. **Common incorrect:** “Catch every Error and show retry.” **Follow-up:** Validation error example? **Related:** [Error architecture](../architecture-and-production.md#86--error-architecture).

**Q270. Why wrap errors with `cause`?** — **Expected:** Translate abstraction while preserving underlying diagnostic chain. **Reasoning:** Caller sees domain contract; logs keep root cause. **Common incorrect:** “Duplicate error for no reason.” **Follow-up:** Where log it? **Related:** [Error architecture](../architecture-and-production.md#86--error-architecture).

**Q271. Why avoid logging same error at every layer?** — **Expected:** Creates duplicate noisy events without ownership/context; log where enough context exists and observability policy owns it. **Reasoning:** Error propagation isn't logging propagation. **Common incorrect:** “Every catch must console.error.” **Follow-up:** What should intermediate layers do? **Related:** [Error architecture](../architecture-and-production.md#86--error-architecture).

**Q272. How should cancellation appear in error architecture?** — **Expected:** Distinguish intentional cancellation/abort from genuine failures so UI/log/retry behavior differs. **Reasoning:** Abort is often control flow. **Common incorrect:** “Report AbortError as production incident.” **Follow-up:** When can abort itself indicate bug? **Related:** [Error architecture](../architecture-and-production.md#86--error-architecture).

**Q273. What is idempotency in client retry design?** — **Expected:** Repeating operation produces no additional unintended effect under defined contract, or API provides idempotency key semantics. **Reasoning:** Retrying POST/payment blindly can duplicate action. **Common incorrect:** “Retries are safe if Promise rejected.” **Follow-up:** Which HTTP methods are generally intended idempotent? **Related:** [Browser fetch](../paradigms-patterns-browser.md#56--browser-fetch-and-http-client-javascript).

**Q274. How can a fluent API be misleading?** — **Expected:** Chain can hide mutation, network I/O, expensive work, or timing; contract should make side effects/async boundaries clear. **Reasoning:** Readability isn't just chaining. **Common incorrect:** “Fluent APIs are always best UX.” **Follow-up:** Builder vs executing chain? **Related:** [API design](../architecture-and-production.md#79--api-design-in-javascript).

**Q275. What is backward compatibility beyond signatures?** — **Expected:** Behavior, timing/order, errors, side effects, accepted input, serialization and observable semantics can be contracts too. **Reasoning:** Consumers depend on behavior. **Common incorrect:** “Same function names means compatible.” **Follow-up:** Deprecation strategy? **Related:** [Library authoring](../architecture-and-production.md#88--library-authoring).

## Senior design scenarios

**Q276. Search UI returns older query after newer query; fix?** — **Expected:** Abort obsolete request when possible and/or use monotonically increasing request identity so only current generation commits state. **Reasoning:** Completion order not request order. **Common incorrect:** “Increase debounce.” **Follow-up:** What if server cannot abort? **Related:** [Concurrency](../architecture-and-production.md#85--concurrency-and-race-conditions).

**Q277. A feature mounts/unmounts repeatedly and listeners double; architecture fix?** — **Expected:** Give feature lifecycle ownership with teardown/AbortController, make mount idempotent or scoped, test repeated cycles. **Reasoning:** Effects need lifetime boundaries. **Common incorrect:** “Call removeEventListener with new anonymous function.” **Follow-up:** Why anonymous mismatch fails? **Related:** [Browser events](../paradigms-patterns-browser.md#54--browser-events).

**Q278. App freezes while parsing/aggregating huge dataset; options?** — **Expected:** Profile; improve algorithm, chunk cooperative work, or move CPU-heavy work to Worker with transfer/structured clone. **Reasoning:** Async Promise wrapper alone doesn't move CPU. **Common incorrect:** “Put loop inside async function.” **Follow-up:** When Worker overhead outweighs benefit? **Related:** [Web Workers](../paradigms-patterns-browser.md#60--web-workers).

**Q279. A module imports a service singleton globally and tests are hard; redesign?** — **Expected:** Introduce dependency injection/port at feature/use-case boundary, keep concrete adapter at composition root. **Reasoning:** Explicit dependency enables isolation/replacement. **Common incorrect:** “Mock ES module internals everywhere.” **Follow-up:** Functional core/imperative shell? **Related:** [Architecture](../architecture-and-production.md#87--large-javascript-application-architecture).

**Q280. When should you reject a clever abstraction?** — **Expected:** When it hides domain behavior, adds indirection without demonstrated reuse/variation, worsens debugging/typing/performance, or locks future design. **Reasoning:** Abstraction has maintenance cost. **Common incorrect:** “More abstraction is more senior.” **Follow-up:** What evidence justifies extraction? **Related:** [Anti-patterns](../internals-performance-debugging.md#76--javascript-anti-patterns).
