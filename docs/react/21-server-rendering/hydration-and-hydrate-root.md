# Hydration and `hydrateRoot`

Server rendering can send useful HTML before the browser has downloaded and executed the React application.

Hydration is the step where React attaches behavior to that existing server-rendered DOM and turns it into a live React application.

The key mental model is:

```text
server
React tree
   ↓
HTML
   ↓
network
   ↓
browser already has DOM
   ↓
hydrateRoot
   ↓
React connects component logic to existing DOM
```

React is not supposed to throw away correct server HTML and rebuild the page from scratch.

## `hydrateRoot`

```jsx
import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';

hydrateRoot(
  document.getElementById('root'),
  <App />
);
```

Use `hydrateRoot` when the container already contains HTML previously generated by React on the server.

For a client-only application with an empty container, use `createRoot` instead.

## `createRoot` vs `hydrateRoot`

```text
createRoot
container starts as client-owned React surface
React renders the DOM

hydrateRoot
container already contains server-generated React HTML
React reuses that DOM and attaches behavior
```

Using the wrong API changes the ownership model.

## The first client render must match

Hydration assumes the client renders the same initial UI the server rendered.

Example server output:

```html
<button>Count: 0</button>
```

The initial client render should conceptually produce the same result:

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>Count: {count}</button>;
}
```

React can then attach the click behavior to the existing button.

## Hydration mismatch

A mismatch happens when server HTML and the first client render disagree.

Common causes include:

- `Date.now()` during render;
- `Math.random()` during render;
- locale-dependent formatting without a shared locale;
- reading `window` during render;
- server and client using different data snapshots;
- browser extensions mutating HTML;
- invalid HTML nesting corrected by the browser;
- conditional client-only rendering that changes markup immediately.

Example:

```jsx
function Clock() {
  return <p>{Date.now()}</p>;
}
```

The server and client almost certainly produce different values.

That violates deterministic initial rendering.

## Prefer deterministic first render

If a value is truly client-only, use a stable server-compatible initial state and update after hydration when appropriate.

```jsx
function OnlineStatus() {
  const [online, setOnline] = useState(null);

  useEffect(() => {
    setOnline(navigator.onLine);
  }, []);

  if (online === null) {
    return <span>Checking connection…</span>;
  }

  return <span>{online ? 'Online' : 'Offline'}</span>;
}
```

The server and first client render both show the same placeholder.

After hydration, the Effect can synchronize with the browser environment.

## Do not use Effect as a universal mismatch patch

A two-pass client-only pattern has a cost:

```text
server renders placeholder
browser receives placeholder
hydrate placeholder
Effect runs
render actual UI
```

That can cause visual changes and extra work.

Use it only for truly browser-only information.

Prefer passing deterministic data from the server when possible.

## `suppressHydrationWarning`

React supports an escape hatch for intentionally different text/content in narrow cases.

```jsx
<time suppressHydrationWarning>
  {new Date().toLocaleTimeString()}
</time>
```

This should not become a general mismatch silencer.

A mismatch often indicates a real server/client data consistency bug.

## Hydration is not "running the server HTML again"

Hydration connects a React tree to existing DOM.

React still renders components conceptually so it knows what the UI should be, but the goal is to reuse compatible DOM rather than replacing it.

This matters when debugging performance:

```text
HTML already exists
≠
React has no hydration work
```

The browser still needs JavaScript, component evaluation, event setup, and React runtime work.

## Root options and production error handling

`hydrateRoot` supports error callbacks such as recoverable-error reporting.

A production app may route these errors into observability tooling while preserving useful console output.

The important design principle is:

- hydration errors are application/runtime signals;
- they should be monitored;
- suppressing warnings without fixing the source hides correctness problems.

## `identifierPrefix`

Server and client may use an identifier prefix to keep generated IDs consistent when multiple React roots share a page.

This is relevant to APIs such as `useId`.

The prefix must agree between server rendering and hydration.

```text
server identifier prefix
must equal
client hydration identifier prefix
```

Otherwise generated IDs can diverge.

## Multiple roots

A page can contain more than one React root.

```jsx
hydrateRoot(document.getElementById('header-root'), <Header />);
hydrateRoot(document.getElementById('app-root'), <App />);
```

Each root is an independent React root.

If generated IDs can appear across roots, use deliberate prefixes.

## Calling `root.render` during hydration

`hydrateRoot` returns a root object.

```jsx
const root = hydrateRoot(container, <App />);
```

Later, the root can render updates.

However, calling `root.render` before hydration has completed can cause React to clear the existing server HTML and switch the root to client rendering.

That destroys the main benefit of hydration for that root.

Do not treat `root.render` as a normal initialization step after `hydrateRoot`.

## `root.unmount`

```jsx
root.unmount();
```

Unmounting detaches React from the root DOM node and cleans up the tree.

This matters in hybrid pages where another system may remove a DOM region containing a React root.

Examples:

- legacy tabs;
- micro-frontends;
- CMS blocks;
- widgets mounted/unmounted by non-React code.

Tell React before the external system destroys its root node so React can clean up subscriptions and component state correctly.

## Hydration + Suspense

Suspense changes hydration architecture significantly.

A streaming server response can send:

1. an initial shell;
2. fallback UI for pending boundaries;
3. later HTML for completed boundaries;
4. scripts/instructions that place completed content correctly.

The browser can begin displaying useful content before the entire tree is complete.

Hydration then coordinates with those boundaries rather than requiring one all-or-nothing page.

This is one of the major reasons modern server rendering uses streaming APIs instead of only `renderToString`.

## Hydration does not mean every component becomes interactive

This distinction becomes especially important with Server Components.

Traditional SSR:

```text
component runs on server to create HTML
component code also exists on client
client hydrates it
```

Server Components:

```text
Server Component runs in server environment
its component implementation is not sent for client execution
Client Component boundaries provide interactivity
```

SSR and Server Components are related but different concepts.

## Data consistency

One of the most important production hydration rules is:

> The client must start from the same logical data snapshot the server used to generate the HTML.

If the server renders user `A` but the browser immediately initializes with user `B`, hydration becomes inconsistent.

Common strategies include:

- embedding serialized initial data;
- framework-provided loader data;
- server/client cache dehydration and rehydration;
- using the same route parameters and locale;
- versioning data when stale responses are possible.

## Browser-only APIs

Do not read browser-only state during server rendering:

```jsx
const width = window.innerWidth;
```

There is no `window` in a normal server environment.

Even a guard can create mismatched markup:

```jsx
const isBrowser = typeof window !== 'undefined';
return <p>{isBrowser ? 'Client' : 'Server'}</p>;
```

The server renders `Server`, while the first client render renders `Client`.

That is still a mismatch.

## Invalid HTML can cause mismatches

Browsers repair invalid markup.

If React server output conceptually contains invalid nesting, the DOM the browser constructs may differ from the structure React expects to hydrate.

This is why hydration debugging should inspect the actual browser DOM, not only the JSX source.

## Hydration and user interaction

Modern React can prioritize hydration work as users interact with the page, especially around Suspense boundaries.

The practical architecture lesson is:

- send useful HTML early;
- keep interactive boundaries intentional;
- avoid shipping client JavaScript for purely static work when the framework can keep it server-only;
- avoid giant all-or-nothing hydration roots when architecture allows more granular boundaries.

## Debugging hydration mismatches

When a mismatch appears, compare these inputs:

```text
server render inputs
props
route params
data snapshot
locale/timezone
feature flags
random/generated values

client first-render inputs
props
route params
hydrated data
locale/timezone
feature flags
random/generated values
```

Then inspect:

1. whether render is deterministic;
2. whether browser-only APIs are read during initial render;
3. whether HTML nesting is valid;
4. whether server and client use the same data;
5. whether external code changed the DOM before hydration.

## Common mistakes

### Mistake: use `createRoot` on server-rendered HTML

That treats the container as a client-rendered root rather than hydrating it.

### Mistake: render timestamps/random values directly

Server and client output diverge.

### Mistake: ignore mismatch warnings

A visible page can still contain broken assumptions, lost state, or incorrect event attachment.

### Mistake: make everything client-only to avoid SSR complexity

That sacrifices server-rendering benefits rather than fixing the data/render contract.

### Mistake: call `root.render` immediately after `hydrateRoot`

This can replace the server HTML with client rendering before hydration finishes.
